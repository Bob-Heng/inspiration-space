# 01 项目目标与边界

## 为什么做

原系统（AI 客户端定时任务 + Prompt + Docx）验证了业务规则，但载体层面痛点明显：

- 每次操作要打开 AI 客户端、找 Prompt、复制粘贴、等待、再打开 Docx 检查状态、手工维护执行时间行；
- 定时任务在电脑关机时被跳过，靠"状态门 + 手动执行检查"补救，可靠性弱；
- Docx 作为数据库，查询、筛选、关系展示、版本管理能力几乎为零；
- 审议交互依赖常驻对话框，讨论记录与库操作耦合在自由文本里。

v2 把业务规则迁移到"数据库 + 后端领域逻辑 + AI 服务 + Web 图形界面"的单机应用，消除上述载体痛点。

## 给谁做

单用户个人知识系统。数据默认属于一个用户；不做组织协作权限，但数据模型不得妨碍未来扩展多用户。

## 术语与核心流程

**术语**：灵感 = 未经审议的条目（待审队列）；观点 = 完成审议的条目（观点库）。审议是"灵感 → 观点"的唯一转化通道。

**输入双通道**：

1. **主通道——界面直接输入**：录入入口内嵌在审议页（待审队列栏）与首页快捷入口，录入即入待审队列，自动独立编号；
2. **辅通道——外部 docx 导入**：用户上传 docx 文档，AI 将其拆解归纳为逐条灵感，入待审队列。

**灵感留档**：灵感入库后永久保留。审议的"修改后采纳"只改写观点正文，灵感原文不动——它是修改前的底稿。留档仅供追溯（观点详情中反查来源灵感），预期使用频率低，不设独立的灵感界面。

原系统的"定时摄取"整体取消，不再需要摄取水位与执行时间记录。相似性 / 再现检查不在录入时做，合并到审议环节的 AI 分析（相近/冲突关系判断）中。

## 解决什么问题（成功标准）

v2 一阶段完成后：

1. 录入、审议、查阅全部在 Web 界面内完成，不再需要打开 AI 客户端粘贴 Prompt；
2. 原系统 Docx 数据（待审观点、原始观点）完整迁移入库，可追溯（观点 → 来源灵感 → 审议会话 → 用户决定）；
3. AI 的任何输出不直接写库，正式变更必须经用户确认 + 后端事务。

## 范围

### 一阶段必须实现

- Web 图形化操作（单机应用，简单密码 + Session）
- 灵感管理：界面直接录入（主）+ docx 导入 AI 拆解（辅），待审队列独立编号
- AI 审议分析（采纳理由 / 最强反对理由 / 分层标签建议 / 相近冲突关系 / 第一轮疑问）
- 图形化审议工作台（队列 + 讨论 + 决策）
- 观点管理：状态机（采纳/悬置/否定）、相近/冲突/合并关系
- 分类观点视图（道/法/术查询视图，否定不列入）
- 原 Docx 历史数据迁移；观点库 Docx 导出

### 暂缓（冻结至后续阶段）

- 碰撞模块、派生观点、世界观建构（原系统中从未真实运行，规则未经校准）
- 定时任务调度与执行检查（随碰撞/世界观模块一起启动）
- 派生观点状态自动推导（随碰撞模块一起实现）

### 明确不做

- 多人实时协作、复杂权限系统
- 手机原生 App、社交分享、开放公共知识社区
- AI 自动替用户完成最终观点裁决
- 附件对象存储（图片/PDF/音视频）

## 硬约束

- 规则优先级：用户决策 > 设计说明书 > 原系统规范（见 README）。
- 单用户、本机运行、单机部署；数据量预期：观点百级、灵感数十条/月，技术决策按此量级评估复杂度。
- 数据库为事实源；Docx 仅为迁移输入、导入素材与导出格式。
